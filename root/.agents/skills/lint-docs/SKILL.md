任意のドキュメントに日本語の文体・表記ルールを適用し、指摘を報告する。必要なツールとルールはこのスキル側が持つ。**対象リポジトリには設定ファイルも依存も一切追加しない。**

**出力言語: 全て日本語で記述すること。** ファイルパス・ルール ID・コマンドはそのまま記載してよい。

## このスキルの境界

**既定は検査のみ。** ユーザーが明示的に修正を依頼したときだけファイルを書き換える。git 操作（`git add` / `git commit` / `git push`、`gh pr create` / `edit` など）は一切行わない。

**この境界は自分で守るルールであり、実行環境に依存しない。** frontmatter の `allowed-tools` を尊重しないホストがある（Codex は `name` と `description` しか読まない）。そうしたホストでは上記の git / gh コマンドが事前承認済みで、確認プロンプトなしに実行される。**プロンプトが出ないことは許可を意味しない。**

## ツール

```bash
textlint-docs "**/*.md"          # 検査
textlint-docs --fix docs/foo.md  # 自動修正
textlint-docs --format json ...  # textlint のオプションはそのまま通る
```

`textlint-docs` は dotfiles の `bin/textlint-docs`（`~/.local/bin` にリンク）。ルールは `dotfiles/textlint/textlintrc.yml`、表記辞書は `dotfiles/textlint/prh.yml`、対象外は `dotfiles/textlint/textlintignore`。依存はキャッシュディレクトリへ隔離して導入されるため、検査対象のリポジトリは一切汚れない。初回だけ npm install が走る（ネットワークが必要）。

コマンドが見つからない場合は `relink` を案内する（dotfiles にファイルはあるがシンボリックリンクが未作成）。

## 手順

### 1. 対象を決める

**候補を集める。** 引数でパスが指定されていればそれを使う。指定がなければ次の順で決める。

1. 未コミットの変更がある Markdown（`git status --porcelain` から抽出）
2. それも無ければ対象を聞く。リポジトリ全体（`"**/*.md"`）を無断で走らせない

**グロブの死角に注意する。** textlint の CLI グロブはドット始まりのディレクトリを辿らない。`.github/`、`.agents/`、`docs/` 配下でもドット始まりの親を持つ文書は `"**/*.md"` では**一件も拾われず、エラーも出ない**。心当たりのある場所は `git ls-files "*.md"` で一覧を取り、明示パスで渡す。

**日本語の文書だけに絞る（省略しない）。** ルールセットに言語判定は無い。`sentence-length` と `max-comma` は英語の文にも当たるため、英語文書を対象に含めると誤検知が支配的になる。実測では、英語 28 ファイルを含む skill 群全体に当てると 345 件出たが、日本語 4 ファイルに絞ると 13 件だった。**残り 332 件はすべてノイズである。**

判定は句点「。」の密度で行う。

```bash
# 各ファイルの 「。」出現数 / 行数 を出す
for f in <候補...>; do
  printf '%4d %4d %s\n' "$(rg -oI '。' "$f" | wc -l)" "$(rg -c '' "$f")" "$f"
done
```

行数に対する句点の比が **5% 未満なら英語文書として対象から外す**。この閾値には実測上かなりの余裕がある（dotfiles で測ると日本語 34〜87%、英語文書は 28 ファイルすべて 0%）。

ひらがなの有無で判定してはいけない。frontmatter の `description` に日本語の起動トリガーだけを持つ英語文書（本文は全て英語）を日本語と誤判定する。実例として `deep-dive/SKILL.md` はひらがな判定では日本語側に落ちるが、句点密度では 0% になる。

逆の取りこぼしもある。箇条書きと体言止めだけで句点を使わない日本語文書は 0% になる。候補にひらがなを含みながら句点密度が低いファイルがあれば、機械判定に委ねず中身を見る。

**何を対象にし、何を外したかを最初に明示する。** 除外したファイル数と、その理由（英語文書・グロブの死角）を報告に含める。

### 2. プロジェクト固有の設定を確認する

対象リポジトリに `.textlintrc*` があるか確認する。**あればプロジェクトの設定が正である。** その場合はこのスキルのルールを上書き適用せず、次のように扱う。

- プロジェクトに lint コマンド（`yarn lint:docs` 等）があればそれを実行する
- スキル側のルールも併せて見たい場合は、両者の差分が意味を持つことをユーザーに伝えてから実行する

プロジェクト固有の設定が無いときだけ、`textlint-docs` をそのまま使う。

### 3. 検査する

```bash
textlint-docs <対象>
```

終了コードは textlint のもの（0 = 指摘なし、1 = 指摘あり、2 以上 = ツールの失敗）。2 以上のときは指摘ゼロと報告しない。

### 4. prh の指摘は「方向」を実測してから採用する

`dotfiles/textlint/prh.yml` は 2 部構成である。

- **セクション A**（誤変換・直訳新造語・業界標準語）: 方向が文書に依存しない。そのまま採用してよい。
- **セクション B**（カタカナ長音などの表記ゆれ）: `expected` は別のリポジトリで数えた多数派であり、一般的な正解ではない。**対象プロジェクトでの実測なしに採用しない。**

セクション B の規則が指摘に出たら、対象プロジェクトでの出現数を数える。

```bash
# 例: サーバー / サーバ の実測（-o で出現数、-I でファイル名を出さない）
rg -oI --pcre2 'サーバー' -g '*.md' . | wc -l
rg -oI --pcre2 'サーバ(?!ー|レス)' -g '*.md' . | wc -l
```

判断は次のとおり。

- 辞書の `expected` が対象でも多数派 → 指摘を採用する
- `expected` が少数派だった → **修正しない。**「辞書の方向が対象プロジェクトと逆である」と報告し、辞書側を直す選択肢を示す
- 拮抗している（どちらも同程度） → 修正せず、表記が割れている事実だけを報告する。どちらへ寄せるかは書き手の判断

実測結果は報告に数値付きで含める。

### 5. 修正する（明示的に依頼されたときだけ）

`--fix` が直せるのは、ひらき系 3 ルールと prh だけである。文長・AI 文体パターンは人手で直す。

修正の手順。

1. 作業ツリーが clean か確認する（`git status --porcelain`）。dirty なら、修正が既存の変更と混ざることをユーザーに伝えてから進める
2. 手順 4 で「採用しない」と判断した prh 規則が対象ファイルに含まれるなら、`--fix` を全体に当てない。該当箇所を避けて Edit で個別に直す
3. `textlint-docs --fix <対象>` を実行する
4. **`git diff` を必ず読み、意図しない置換が無いか確認する。** prh は正規表現置換であり、コードブロック外の固有名詞・引用文を巻き込むことがある
5. 巻き込みがあれば元に戻し、その箇所は `<!-- textlint-disable ルールID -->` 〜 `<!-- textlint-enable -->` で囲んで理由を添える

### 6. 報告する

```
## ドキュメント検査: [対象の説明]

### 概要
- 対象: [パスまたはグロブ]（日本語 N ファイル）
- 対象外: N ファイル（英語文書 N / グロブの死角 N）
- 指摘: N 件（うち自動修正可能 N 件）
- プロジェクト固有の textlint 設定: あり / なし

### 要対応
- [ファイル:行] 指摘内容と、なぜ直すべきか

### 表記ゆれ（実測つき）
- [語] 対象での出現数 A : B。辞書の方向と一致 / 不一致

### 判断保留
- [ファイル:行] ルールには反するが、文脈上は正当と考えられる箇所とその理由
```

該当のないセクションは省略してよい。

## 指摘の扱い方の原則

**既存文書を正とし、ルールを文書に合わせる。** 機械の指摘は仮説であって判定ではない。次のいずれかに当たるときは、文書ではなくルールを疑う。

- 同じ規則が広範囲で大量に出る → 閾値・方向がそのプロジェクトの実態と合っていない可能性が高い。`dotfiles/textlint/textlintrc.yml` の調整を提案する
- 引用文・固有名詞・外部からの転載が違反している → 文書は直さず、理由を添えた `textlint-disable` コメントで囲む
- ルール自体が壊れている → 例として `ja-no-redundant-expression` はノード境界をまたいで誤マッチし `--fix` が文章を破壊するため無効化してある。同種の挙動を見つけたら報告する

- **ひらき系ルールが品詞を取り違えている** → `ja-hiragana-fukushi` は形容詞「正しい」の連用形「正しく」を副詞「正しく（＝まさしく）」と誤認する。「句点密度では正しく 0% になる」に対して「まさしく」への置換を提案し、これは**自動修正対象**なので `--fix` を無警戒に当てると意味が壊れる。同様に「最も」→「もっとも」も、公用文の漢字使用基準では漢字書きが標準でルールの方が過剰である。ひらき系の指摘は、置換後の語を文に戻して読んでから採用する

`textlintignore` に個別ファイルを足して違反を回避しない。除外はカテゴリ単位の設計判断だけに使う。
